## F2-BACK-19 — LazyInitializationException da maré (commit `12e0a1a`)

Causa: `TideServiceImpl.getCurrentTideHeight` chamava `getTideHeightAt` por auto-invocação, sem passar pelo proxy; o `@Transactional` de `getTideHeightAt` não valia e `TideTable.geoLocations` (e `months`/`days`/`hours`, todos LAZY) eram lidos fora de sessão. Correção: `@Transactional(readOnly = true)` no ponto de entrada; mapeamento continua LAZY. Teste `PredictionCycleTideIntegrationTest` (TideService real, tábua persistida): falha sem a anotação, passa com ela. Na API real: ciclo `predict-ana` às 20:03 (UTC-3 de log) gravou "Previsões atualizadas para 5 ponto(s) ativo(s)" e `grep -c LazyInit` no log = 0.

## F2-BACK-20 — `geocode_level` e `neighborhood` (commit `672b519`)

`V11__occurrence_geocode_level.sql`, aditiva (2 `ADD COLUMN` nuláveis + `CHECK` em STREET/NEIGHBORHOOD/CITY/NONE). Não renumerar: a branch `feat/pipeline-mare` usa V12 sobre ela. O nível vem do tipo do objeto que o Nominatim devolveu (`addresstype`/`type`/`class`), não da consulta que o achou; sem tipo, vale o nível da consulta. `neighborhood` é o campo `Bairro` do bruto.

Legado (`POST /api/admin/ingestion/ckan/backfill-geocode-level`): o geocodificador não guardou o resultado, então o nível só é gravado se uma nova consulta devolve exatamente a mesma coordenada gravada (±1e-5°); senão fica NULL (não se inventa). Sem coordenada seria NONE (nenhum caso). Das 591 linhas legadas: 264 STREET, 132 NEIGHBORHOOD, 195 NULL (não verificável); bairro preenchido nas 591.

Distribuição nas ocorrências canônicas (menor `id` por `_id`+data):

| Nível | 197 legadas | 28 de 2022 | Total 225 |
|---|---|---|---|
| STREET | 88 | 28 | 116 |
| NEIGHBORHOOD | 44 | 0 | 44 |
| CITY | 0 | 0 | 0 |
| NONE | 0 | 0 | 0 |
| NULL (legado não verificável) | 65 | 0 | 65 |

STREET aqui é rua sem número: várias ocorrências da mesma rua dividem a coordenada. As 65 NULL não devem ser lidas como rua nem como bairro; 47 delas dividem coordenada com endereços distintos (sinal de centróide, não gravado como nível).

## F2-BACK-17 — desempenho do export (commit da tarefa 4)

Endpoint e período fixos: `GET /api/export/ia-dataset/CIN_UFPE/csv?days=1825&to=2026-10-01T00:00:00Z`, 10 chamadas sequenciais (`bench.sh`; saídas em `F2-BACK-17-bench-*.txt`). Com 10 amostras o p95 é o máximo.

### Diagnóstico

`EXPLAIN (ANALYZE, BUFFERS)` das consultas do export (plano completo em `F2-BACK-17-explain.txt`): view horária de clima 5 anos/1 ponto: 594 ms (306 768 linhas, ordenação em disco de 25 MB, 19 625 buffers); solo ERA5: 81 ms; ocorrências casadas: 0,03 ms; sensores: 1,2 ms. O SQL soma menos de 0,7 s dos ~11 s: a view horária **não** é o gargalo, e compressão/continuous aggregate não se justificam (nenhuma migração foi criada para isso).

O gargalo está no Java: para cada uma das ~43 800 horas, `TideServiceImpl.getTideHeightAt` faz `findAllByYear` (consulta ao banco), grava logs INFO e, nos anos sem tábua local (só 2026 tem), delega à API externa TabuaMare. Cada export gerava ~81 mil linhas de log. Pior: o cache `tideTableDaily`/`tideNearestHarbor` era despejado a cada 10 min (`CacheConfig`), então ~1 export em 3 a 10 refazia ~1 800 chamadas HTTP (35 a 49 s), e com o circuit breaker aberto o CSV mudava de hash entre chamadas (5 hashes distintos em 10 chamadas).

### Medidas aplicadas (as menores que resolvem)

1. Logs por hora de maré de INFO para DEBUG (`TideServiceImpl`, `TabuaMareServiceImpl`).
2. `tideNearestHarbor`/`tideTableDaily` fora do despejo de 10 min e sem cachear respostas de erro (`unless`).
3. Export usa `TideService.getStoredTideHeightAt` (só tábua local sincronizada, sem chamada externa). **Muda o conteúdo**: nos anos sem tábua local a coluna `tideHeight` sai vazia (antes vinha da API externa quando disponível; com a API fora do ar já saía vazia). Decisão do autor: manter, ou sincronizar tábuas locais de 2021–2025 (`/api/admin/.../tide sync`) para ter maré no histórico. O manifesto declara a fonte.

Ainda restam ~3 s em Java (montagem da timeline, `isTimeWithinEvent` por hora, `builder.build()` dentro do laço de sensores, uma consulta `findAllByYear` por hora); não otimizados por estarem dentro da meta.
