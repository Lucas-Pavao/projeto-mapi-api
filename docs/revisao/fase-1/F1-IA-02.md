### 1.2 Causas concretas do "não funcional" (por ordem de gravidade)

1. **Skew treino/serviço de 9 de 28 features** (crítico). `FEATURE_COLUMNS` (`AI:mapi_ai/feature_engineering.py:10-39`) inclui `wind_speed, temperature, apparent_temperature, humidity, pressure, wave_height, wave_period, wave_direction, solar_radiation`. No treino elas vêm da tabela `flood_scenario_labels` (preenchidas em `API:service/impl/MapiServiceImpl.java:~640-690`). Na inferência o `PredictionInput` as define com default `0.0` (`AI:mapi_ai/app.py:72-81`) e o DTO enviado pelo backend **não tem esses campos** (`API:dto/FloodPredictionRequestDTO.java:93-125`). Resultado: `pressure=0` hPa, `humidity=0`, `temperature=0` entram no `StandardScaler` e saem como z-scores de dezenas de desvios; a saída do XGBoost é ruído extrapolado.
2. **Tarefa errada para o objetivo** (crítico). Ver seção 2.
3. **Fallback silencioso para dado sintético** (crítico). `AI:mapi_ai/trainer.py:96-98`: se CSV e banco falharem ou vierem vazios, `generate_dummy_scenario_data()` (`trainer.py:18-71`, rótulo = função determinística de chuva, maré e rio, `:44-45`) é usado sem abortar. Um `.joblib` treinado assim parece legítimo. Sem metadata não há como saber se os binários atuais vieram disso.
4. **Cache espacial vazio é permanente** (importante). `lifespan` (`app.py:35-41`) chama `cache.load_from_db()`; se o banco estiver fora no boot, `load_from_db` engole a exceção (`feature_engineering.py:70-72, 111-113`) e deixa listas vazias. Em inferência `is_training=False` nunca recarrega (`feature_engineering.py:278`). Fica `altitude=10.0`, `distance_to_channel=100.0` e, pior, `distance_to_flood_point=0.0` (`:164-166`), que significa "em cima de um ponto crítico".
5. **`distance_to_channel` é constante mesmo com banco OK** (importante). A tabela tem a coluna `distance_to_channelm` (`API:.../V1__baseline_schema.sql:161`), mas o código procura `distance_to_channel_m, distancetochannelm, dist_canal_m, distance_to_channel, distanceToChannelM` (`feature_engineering.py:94`). Nenhum nome casa, então cai sempre no default `100.0`. A feature é inútil. (`altitudem` casa em `:84`.)
6. **Banco no caminho de inferência** (importante). `predict_river_level_lstm` abre engine e consulta `flood_scenario_labels` a cada requisição (`app.py:118-128`), com `f-string` em SQL (`:121-127`; valores são `float`, injeção improvável, mas é má prática) e sem pool reutilizado.
7. **Dependências não travadas** (importante). `AI:requirements.txt` lista 13 pacotes sem versão. `joblib.load` de XGBoost/sklearn e `load_model` de Keras quebram entre versões; falha seria silenciada em `app.py:18-21`/`:31-33`, resultando em 503 permanente. `geopandas` e `shapely` não são importados em nenhum `.py`.
8. **Caminhos relativos** (desejável). `AI:mapi_ai/config.py:21-23` (`models/...`) só funciona com cwd na raiz; o `Dockerfile` usa `WORKDIR /app`, então OK no container. `main.py:19` usa `reload=True` em modo serve (não é configuração de produção).

## 5. Contrato `/v1/predict/flood` e degradação ponta a ponta

### 5.1 Entrada da IA (Pydantic) — `AI:mapi_ai/app.py:45-84`

- Obrigatórios: `station_id`, `current_rainfall`, `rainfall_3h/6h/12h/24h_accumulated`, `tide_level`, `timestamp` (`str` sem validação de formato).
- Opcionais com default silencioso: `river_level=0.0`, `wind_speed`..`solar_radiation=0.0`, `nearby_sensors=[]`.
- `lat`/`lon`/`latitude`/`longitude` todos `float = None`; a resolução está em `app.py:94-98`. Faltando ambos os pares: `ValueError` dentro de `prepare_features_for_inference` → capturado em `:183` → **HTTP 500** com `detail=str(e)` (deveria ser 422).
- Sensor próximo: `latitude`/`lat`, `longitude`/`lon`, `distanceKm`/`distance_km` (aliases duplicados, `:45-55`); `value`, `unit`, `type` obrigatórios, então um sensor com `value=null` derruba a requisição inteira com 422.
- Valor `null` explícito em campo `float` com default (ex.: `river_level: null`) é rejeitado pelo Pydantic (o default só vale para campo ausente).

### 5.2 Saída da IA

```json
{ "flood_probability": 0.0-1.0, "risk_level": "LOW|MEDIUM|HIGH",
  "station_id": "...", "timestamp": "<eco>", "predicted_river_level": 0.0 }   // último só se LSTM ok

Limiares: `prob > 0.8` → HIGH, `> 0.5` → MEDIUM, senão LOW (`app.py:164-168`). Não existem `modelVersion`, `topContributors`, `message`, `estimated_time_to_event` nem horizonte.

- Falha de qualquer tipo (timeout inexistente, conexão recusada, 4xx/5xx, corpo vazio) → `unknownResult` (`:38-39`, `:48-51`, `:54-60`): `floodProbability=0.0`, `riskLevel="UNKNOWN"`, `message="Erro na comunicação com o modelo de IA: " + e.getMessage()` (a mensagem da exceção, incluindo o `detail` interno da IA em 500, vai ao cliente).
- Auditoria: `MapiServiceImpl.java:154-171` grava `flood_predictions` com `risk_level="UNKNOWN"`, `flood_probability=0.0`, `status="FAILED"` e a mesma `message`. O comentário da entidade (`API:model/FloodPrediction.java:232`) cita um terceiro status `UNKNOWN` que nunca é usado. A entrada imputada (maré/rio/acumulados `0.0`) é gravada como se fosse medição.

        A-->>B: 200 {flood_probability, risk_level LOW|MEDIUM|HIGH, ...}
        B->>D: INSERT status=SUCCESS, probabilidade, risk_level
        B-->>F: 201 {floodProbability, riskLevel, estimatedTimeToEvent=null, message=null}
        F->>F: cor por riskLevel (CRITICAL nunca ocorre)
    else IA fora do ar, timeout, 422, 500 ou 503
        A--xB: erro / sem resposta (pode travar sem limite)
        B->>B: catch genérico -> UNKNOWN, prob 0.0, message com e.getMessage()
        B->>D: INSERT risk_level=UNKNOWN, flood_probability=0.0, status=FAILED
        B-->>F: 201 {floodProbability 0.0, riskLevel UNKNOWN, message com texto da exceção}
        F->>F: Popup: cinza "Em Análise" + "0%"
        F->>F: DetailCard: VERDE "Baixo" + "0%"
        F->>F: Marcador no mapa: VERMELHO (padrão)
    else exceção antes da chamada à IA
        B-->>F: 201 com corpo vazio / floodPrediction null
        F->>F: prediction undefined: Popup cinza, DetailCard verde "Baixo"
    end
```

## 6. LSTM

- **O que prevê:** `river_level` do passo seguinte, tendo como entrada a janela de 28 features (que inclui o próprio `river_level`) (`trainer.py:141-203`, `models.py:19-29`). Autorregressão sobre instantâneos de cliques.
- **Usado na inferência?** Sim, se TensorFlow instalado e `.h5` presente: `app.py:178-180` anexa `predicted_river_level` à resposta. O XGBoost não consome essa saída, o backend ignora o campo (`FloodPredictionServiceImpl.java:65-77`) e o front não o conhece. Na prática, é código com custo (TensorFlow na imagem, uma consulta ao banco por requisição) e sem consumidor.
- **Bugs de contrato:**
  - `window_size` no treino é `min(12, len(df)//10)` (`trainer.py:163`); a inferência fixa `12` (`app.py:113`). Com menos de 120 linhas de treino, o shape não bate com o modelo salvo e o `predict` falha; a exceção é engolida (`:149-151`) e o LSTM some da resposta sem aviso. O `scaler` usado no LSTM é o do XGBoost (`app.py:144`), salvo uma só vez em `trainer.py:135`.
  - Ordem cronológica: o ramo de histórico insuficiente usa `df_hist` em ordem `DESC` sem inverter (`app.py:134-137`), enquanto o ramo suficiente inverte (`:140`).
  - A janela mistura linhas de pontos diferentes dentro de ±0,05° (cerca de 5 km), não uma série por ponto.
  - Avaliação de MSE/MAE no mesmo conjunto passado como `validation_data` (`trainer.py:186-198`).
- **Evidência de ganho sobre features agregadas:** **nenhuma.** Não há baseline de persistência (`river_level[t+1] = river_level[t]`), nem comparação com XGBoost de regressão sobre acumulados, nem split de teste independente. Recomendação: tratar como experimento fora da cadeia de produção até haver comparação defensável. `[DISSERTACAO]`: não citar o LSTM como componente validado.
